CONTRATO ALTERADO

Anterior:
- POST /video/projects/render aguardava todo o processamento e retornava HTTP 200 com ProjectResponse.
- GET /video/projects/output/{projectId} exigia x-api-key.

Novo V3.1:
- POST /video/projects/generation cria ou devolve o único generation job do projeto/plano na instância e explicita maxPaidOperations restante.
- GET /video/projects/{projectId}/generation/{generationJobId} consulta o snapshot mais recente sem iniciar outro job.
- O worker reserva a próxima cena no state assinado antes do POST, gera estritamente em sequência e nunca repete POST ambíguo.
- O job termina em assembling; render continua sendo uma Action separada.
- Advance/status/continue permanecem no runtime para compatibilidade, mas não aparecem no OpenAPI do Custom GPT. Advance/continue são bloqueados enquanto existir generation job.
- No runtime legado, POST /video/projects/advance ainda inicia no máximo uma cena e POST /video/projects/status ainda consulta no máximo um status sem POST pago.
- POST /video/projects/continue também permanece somente para compatibilidade; os três endpoints manuais foram removidos do contrato V3.1 do Custom GPT.
- POST /video/projects/render valida o state, agenda o trabalho efêmero e retorna HTTP 202 com projectId, renderJobId e status processing.
- GET /video/projects/{projectId}/render/{renderJobId} retorna JSON com processing, completed ou failed.
- Quando completed, o status inclui o novo projectState e uma downloadUrl absoluta temporária.
- GET /video/projects/output/{projectId}?access=... não exige x-api-key; o acesso é autorizado pelo token HMAC temporário vinculado ao projeto, handle e expiração.

IMPLEMENTAÇÃO

- RenderJobManager mantém o menor estado temporário necessário em Map por instância.
- O processamento pesado inicia fora do lifecycle da requisição que retornou 202.
- Jobs são deduplicados por projectId enquanto permanecem no Map.
- Falhas inesperadas são reduzidas a PROJECT_RENDER_FAILED sem detalhes internos.
- Job metadata expira por TTL; output também possui TTL e cleanup próprios.
- RENDER_EXTERNAL_URL, fornecida automaticamente pelo Render, forma a URL pública. PUBLIC_BASE_URL é um override opcional para outros ambientes.

SEGURANÇA

- Todas as Actions normais continuam protegidas por x-api-key.
- Somente o endpoint binário de download é público por token assinado.
- Token alterado, expirado ou associado a outro projeto é rejeitado.
- Project State e acesso de download exigem Base64URL canônico; representações alternativas são rejeitadas.
- O handle do arquivo é UUID gerado pelo servidor e resolvido somente dentro do diretório de outputs.
- Caminhos internos e secrets não aparecem nas respostas.
- Cache-Control private, no-store e Referrer-Policy no-referrer são enviados no download.

LIMITAÇÕES RESTANTES

- Generation jobs, render jobs e arquivos são efêmeros. Restart/deploy pode interromper trabalho e apagar metadata/output.
- Idempotência é forte somente dentro do processo. Sem storage compartilhado ou idempotency key do provider, token pending antigo reutilizado após restart não pode ser detectado; o cliente deve parar em job perdido.
- O Map é por instância. Escalar para múltiplas instâncias exige job store e object storage compartilhados.
- O GPT deve preservar o Project State mais recente; tokens antigos continuam sujeitos à limitação de replay stateless já documentada.
- O link deixa de funcionar após expiração ou cleanup e não implica armazenamento permanente.
